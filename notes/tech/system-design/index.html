A strong design interview is a guided discussion. Anchor each technical choice to a requirement, an estimate, or a known bottleneck.

A design framework

1 · Scope

Clarify functional and non-functional needs

Who uses it? What are the core operations? Is freshness, availability, latency, durability, or consistency most important? Explicitly defer out-of-scope features.

2 · Estimate

Make scale concrete

Estimate requests per second, read/write ratio, object size, storage growth, and bandwidth. Approximate numbers reveal whether a single database, cache, or asynchronous pipeline is necessary.

3 · Design and refine

Start simple, then find the bottleneck

Draw clients, API, services, data stores, and the main data flow. Then discuss caching, partitioning, replication, queues, observability, and failure modes.

Useful building blocks

Know why each component exists

Load balancer → distributes traffic and enables horizontal scaling Cache → lowers read latency and database load; requires invalidation strategy Queue → absorbs bursts and decouples slow background work Database → durable source of truth; choose relational for joins/transactions CDN → serves static, cacheable content close to users Replication → improves read availability; can introduce replication lag
Trade-off language: “For this read-heavy feed, I would cache popular results. I would accept brief staleness, but invalidate or refresh after a write so users do not see old content for long.”

Worked example: URL shortener

From request to architecture

Requirements: create a short URL, redirect quickly, and optionally record clicks. A client sends POST /urls; a service generates a unique ID, encodes it, and stores the mapping. GET /{code} checks a cache then the primary store and returns a redirect.

Client → load balancer → URL service → cache → key-value store └────────→ event queue → analytics worker Key concern: code collisions. Use a distributed ID generator or retry a random code after a uniqueness check. Cache popular mappings; make analytics async so redirect latency does not depend on logging.

Practice questions

  1. Design a rate limiter: compare token bucket and fixed-window counters. Where would you store counters?
  2. Design a news feed: contrast fan-out on write with fan-out on read for celebrity accounts.
  3. Design file storage: separate metadata from file bytes and explain upload/download flow.
  4. Design a chat service: discuss connection management, delivery order, presence, and offline messages.
