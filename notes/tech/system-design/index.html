A strong system-design interview is a guided discussion. Start with what the product must do, quantify the scale, draw a simple first design, then improve its bottlenecks with a clear reason for every component.

A repeatable interview framework

1 · Scope

Clarify requirements

Ask who uses the product, its core operations, expected scale, and what is out of scope. Separate functional requirements (“create a post”) from non-functional requirements (“p99 reads under 200 ms”).

2 · Prioritise

Name the important qualities

Confirm the priority among latency, availability, consistency, freshness, durability, cost, and security. You cannot optimise every quality at the same time.

3 · Estimate

Make scale concrete

Estimate requests per second, read/write ratio, object size, storage growth, bandwidth, and peak traffic. Round numbers are enough to identify the first bottleneck.

4 · Design

Draw the simple path first

Show clients, API, services, data stores, and the main read/write flows. Define an API and data model before introducing specialised infrastructure.

5 · Refine

Remove the bottleneck

Add caching, indexing, replication, partitioning, queues, and background workers only when a requirement or estimated bottleneck justifies them.

6 · Close

Discuss failure and trade-offs

Explain how the system behaves when a dependency is slow or unavailable, what you monitor, and what you deliberately chose not to solve yet.

Common must-know knowledge

APIs and communication

HTTP/REST suits request-response APIs. WebSockets fit persistent, low-latency bidirectional updates such as chat. gRPC/RPC is common for internal service-to-service calls. Design APIs to be idempotent when clients may retry.

Databases and indexes

Use a relational database for transactions, joins, and strong constraints. Use key-value or document stores for simple high-scale access patterns. Index fields used for lookup, filtering, ordering, or joins; indexes speed reads but add storage and write cost.

Caching

Cache read-heavy or expensive results close to the client or service. Cache-aside is the common default: read cache, fetch on miss, then populate it. Discuss TTL, invalidation after writes, cache stampedes, and the acceptable amount of staleness.

Scaling and partitioning

Scale stateless services horizontally behind a load balancer. Partition data when one database node cannot handle size or throughput. Choose a stable partition key, avoid hot keys, and know how you would rebalance partitions.

Replication and consistency

Replication improves read capacity and availability, but replicas can lag. State whether a user must read their own write, whether stale data is acceptable, and when to route requests to the primary.

Queues and background work

Use a queue to absorb bursts and decouple slow, non-critical work: notifications, analytics, image processing, and email. Consumers need retries, dead-letter handling, idempotency, and a plan for duplicate delivery.

Reliability

Set timeouts, retries with backoff and jitter, circuit breakers, rate limits, and graceful degradation. Do not retry a non-idempotent write blindly. Remove single points of failure where availability is important.

Observability and security

Monitor latency, traffic, errors, saturation, queue depth, cache hit rate, and database health. Use structured logs, metrics, tracing, authentication, authorisation, encryption in transit, and least-privilege access.

Quick estimation cheat sheet

Average requests per second = daily requests / 86,400
Peak RPS                    ≈ average RPS × peak multiplier
Daily storage               = writes/day × bytes per write
Storage over N years        = daily storage × 365 × N
Bandwidth                   = requests/second × average response size

Useful approximations:
1 KB  ≈ 10³ bytes
1 MB  ≈ 10⁶ bytes
1 GB  ≈ 10⁹ bytes
1 day = 86,400 seconds

Say your assumptions out loud. For example: “At 10 million reads per day, average traffic is about 115 reads per second. If peak is 10× higher, I will design the read path for roughly 1,200 RPS.” The estimate need not be exact; it should drive a design decision.

Reusable design templates

Read-heavy lookup

Cached lookup service

Client → CDN / load balancer → API service
                                 ↓
                              cache
                                 ↓ on miss
                            primary database

Use for URL shorteners, profiles, product details, configuration, and public content. Cache popular keys, index the primary lookup key, replicate for read scale, and define invalidation or TTL behaviour after a write.

Write-heavy ingestion

Durable write + asynchronous processing

Client → API service → primary database
                         ↓
                     event queue → workers → search / analytics / notifications

Use for orders, posts, uploads, events, and activity logs. Commit the essential user-visible record first; publish downstream work asynchronously. Make consumers idempotent because events can be delivered more than once.

Large files

Object storage with metadata

Client → API → metadata database
             └→ pre-signed upload URL → object storage → CDN
                                           ↓
                                    processing queue → workers

Use for photos, videos, and documents. Store file bytes in object storage, not the primary database. Keep ownership, file state, and object key in metadata. Upload directly to storage when possible.

Real-time updates

Connection gateway + event fan-out

Client ⇄ WebSocket gateway ⇄ message service
                                  ↓
                            queue / pub-sub
                                  ↓
                         delivery workers / presence store

Use for chat, live notifications, collaboration, and dashboards. Discuss connection ownership, ordering scope, offline delivery, backpressure, and whether messages are persisted before acknowledgement.

Rate limiting

Admission control at the edge

Client → gateway / rate limiter → API service
                    ↓
          distributed counter store

Use token bucket for controlled bursts and steady refill, or sliding/fixed windows for simpler limits. Key by user, API key, IP, route, or a combination. Return a clear retry response when rejecting traffic.

Search and autocomplete

Primary data + derived search index

Write → primary database → change event → indexer → search index
Read  → search API → search index → ranked results

Use when users search text or filter many fields. The search index is a derived, eventually consistent view. Discuss indexing delay, ranking, typo tolerance, and a fallback when the index is unavailable.

Worked example: URL shortener

Requirements and API

Core requirements: create a short URL, redirect quickly, and optionally record clicks. A minimal API is POST /urls to create a mapping and GET /{code} to redirect.

Client → load balancer → URL service → cache → key-value store
                                      └────────→ event queue → analytics worker

The service generates a unique ID, encodes it, and stores code → destination URL. Redirects check the cache first, then the primary store. Use a distributed ID generator or retry random codes after a uniqueness check to avoid collisions.

Cache popular mappings because redirects are read-heavy. Send click logging to a queue so redirect latency does not depend on analytics. Add expiration status to the mapping if links can expire; rate-limit creation to control abuse.

Practice prompts

  1. Rate limiter: compare token bucket, fixed window, and sliding window. Where do counters live, and what happens if the store is unavailable?
  2. News feed: compare fan-out on write with fan-out on read, especially for celebrity accounts.
  3. File storage: separate metadata from file bytes; explain upload, download, processing, and deletion.
  4. Chat service: discuss WebSocket connections, delivery order, presence, offline messages, and reconnects.
  5. Notification service: design preferences, deduplication, retries, channels, and provider failures.
  6. Autocomplete: design the write path to an index, the low-latency read path, and ranking or typo tolerance.
