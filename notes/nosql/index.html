1 · What is NoSQL?

NoSQL stands for "Not Only SQL". It refers to databases that don't rely on the traditional relational (table-based) model used by MySQL or PostgreSQL.

🗂️ SQL Database

Like a highly organized filing cabinet — fixed drawers, folders and labels.

🎒 NoSQL Database

Like a flexible backpack — store anything in any shape, rearrange freely.

🌊 Why Does NoSQL Exist?

Traditional SQL was built in the 1970s–80s for structured, manageable data. The modern web changed everything:

  • 📈 Massive scale — Billions of users (Facebook, Google, Amazon)
  • 🌊 Unstructured data — Social posts, images, logs, sensor data
  • ⚡ High speed — Real-time apps needing millisecond responses
  • 🔄 Flexible data — Data that constantly changes shape

3 · Types of NoSQL Databases

📄 Document Databases

Store data as JSON-like documents. Each document can have a different structure.

MongoDB CouchDB

Use Case: User profiles, product catalogs, blog posts

JSON Document
{
  "name": "Alice",
  "age": 28,
  "hobbies": ["reading", "coding"],
  "address": {
    "city": "New York",
    "zip": "10001"
  }
}

🔑 Key-Value Stores

The simplest type — like a dictionary. Every piece of data is a key → value pair. Extremely fast for lookups.

Redis DynamoDB

Use Case: Caching, sessions, shopping carts

Key-Value Example
"user:101"       → "Alice"
"session:abc123" → "{ logged_in: true, expires: ... }"

📊 Wide-Column (Column-Family) Stores

Store data in columns instead of rows. Great for reading specific columns across millions of rows.

Cassandra HBase

Use Case: Time-series data, analytics, IoT sensor readings

🕸️ Graph Databases

Store data as nodes (entities) and edges (relationships). Perfect when relationships are the focus.

Neo4j Amazon Neptune

Use Case: Social networks, fraud detection, recommendations

Graph Relationship
(Alice) --[FRIENDS_WITH]--> (Bob)
(Bob)   --[LIKES]--> (Movie: Inception)

4 · Core Concepts

  • Schema-less — No need to pre-define data structure; fields can vary per document
  • Horizontal Scaling — Add more servers (nodes) instead of upgrading one big server
  • Eventual Consistency — Data might not be instantly synced across all nodes, but will be eventually
  • CAP Theorem — A NoSQL DB can only guarantee 2 of 3: Consistency, Availability, Partition Tolerance
  • Replication — Data is copied across multiple servers for reliability
  • Sharding — Data is split across multiple servers for performance

5 · CRUD Queries (with DB State)

💡 Using MongoDB with database shopDB and collection products. Starting with an empty collection.

➕ insertOne

JavaScript — MongoDB Shell
db.products.insertOne({
  name: "Wireless Headphones",
  brand: "SoundMax",
  price: 59.99,
  stock: 120,
  tags: ["electronics", "audio"]
})
📦 DB State After
[
  { "_id": "001", "name": "Wireless Headphones",
    "brand": "SoundMax", "price": 59.99,
    "stock": 120, "tags": ["electronics", "audio"] }
]  ← 1 document
💡 MongoDB auto-generates _id for every document.

➕ insertMany

JavaScript
db.products.insertMany([
  { name: "Running Shoes", brand: "SpeedFit",
    price: 89.99, stock: 45,
    tags: ["footwear", "sports"] },
  { name: "Coffee Maker", brand: "BrewKing",
    price: 34.99, stock: 200,
    tags: ["kitchen", "appliances"] },
  { name: "Yoga Mat", brand: "FlexZone",
    price: 24.99, stock: 300,
    tags: ["fitness", "sports"] }
])
📦 DB State After (4 documents total)
_id  name                  price   stock
001  Wireless Headphones   59.99   120
002  Running Shoes         89.99    45
003  Coffee Maker          34.99   200
004  Yoga Mat              24.99   300

🔍 find — Basic Queries

Find All

JavaScript
db.products.find()  // returns all 4 documents

Find with Filter

JavaScript
db.products.find({ brand: "SpeedFit" })

Comparison Operators

JavaScript
// price less than 40
db.products.find({ price: { $lt: 40 } })
OperatorMeaning
$ltLess than
$lteLess than or equal
$gtGreater than
$gteGreater than or equal
$eqEqual to
$neNot equal to

Projection (Select Specific Fields)

JavaScript
// Only return name and price, hide _id
db.products.find({}, { name: 1, price: 1, _id: 0 })
💡 1 = include the field  |  0 = exclude the field

✏️ updateOne & updateMany

updateOne — Change a Value

JavaScript
db.products.updateOne(
  { name: "Coffee Maker" },     // filter
  { $set: { price: 39.99 } }  // update
)
📦 DB State After
003  Coffee Maker   39.99  ← was 34.99, now 39.99 ✅

$inc — Increment / Decrement

JavaScript
// Reduce stock by 5
db.products.updateOne(
  { name: "Running Shoes" },
  { $inc: { stock: -5 } }
)
📦 DB State After
002  Running Shoes  stock: 40  ← was 45, now 40 ✅

updateMany — Add New Field to Multiple Docs

JavaScript
// Add "discount: true" to products under $50
db.products.updateMany(
  { price: { $lt: 50 } },
  { $set: { discount: true } }
)
📦 DB State After
001  Wireless Headphones  59.99  ← NOT affected (price ≥ 50)
002  Running Shoes        89.99  ← NOT affected
003  Coffee Maker         39.99  discount: true ✅
004  Yoga Mat             24.99  discount: true ✅
🤯 Docs 001 & 002 have NO discount field. In SQL this would require a schema change for the entire table — in NoSQL it's perfectly fine!

🗑️ deleteOne & deleteMany

deleteOne

JavaScript
db.products.deleteOne({ name: "Yoga Mat" })
📦 DB State After (3 documents)
001  Wireless Headphones
002  Running Shoes
003  Coffee Maker
004  Yoga Mat  ← GONE ✅

deleteMany

JavaScript
// Delete all products with stock > 100
db.products.deleteMany({ stock: { $gt: 100 } })
📦 DB State After (1 document)
002  Running Shoes  stock: 40
001  (stock: 120) → DELETED
003  (stock: 200) → DELETED

🔗 Advanced Queries

Query Inside Arrays

JavaScript
// Finds all products tagged "sports"
db.products.find({ tags: "sports" })

Logical Operators

JavaScript
db.products.find({
  $or: [
    { tags: "electronics" },
    { price: { $lt: 30 } }
  ]
})
OperatorMeaning
$orAt least one condition is true
$andAll conditions must be true
$notCondition must be false
$norNone of the conditions are true

Aggregation Pipeline

JavaScript
// Average price per tag, sorted highest first
db.products.aggregate([
  { $unwind: "$tags" },
  { $group: {
      _id: "$tags",
      avgPrice: { $avg: "$price" },
      totalProducts: { $sum: 1 }
  }},
  { $sort: { avgPrice: -1 } }
])
⚠️ Always put $match first in your pipeline — filter early to reduce load on later stages.

6 · Flexible / Mixed Schemas

This is one of NoSQL's biggest advantages. Documents in the same collection can have completely different fields.

➕ Insert a Digital Product

JavaScript
db.products.insertOne({
  name: "Photo Editing Software",
  type: "digital",
  price: 149.99,
  license: "annual",
  platforms: ["Windows", "macOS", "Linux"],
  features: {
    aiTools: true,
    cloudSync: true,
    maxProjects: 50
  }
})

➕ Insert a Food Product

JavaScript
db.products.insertOne({
  name: "Organic Green Tea",
  category: "food & beverage",
  price: 12.99,
  nutritionInfo: {
    calories: 2,
    caffeine: "30mg"
  },
  certifications: ["Organic", "Fair Trade", "Vegan"],
  origin: "Kyoto, Japan"
})

📊 Schema Field Comparison

FieldRunning ShoesPhoto SoftwareGreen Tea
price✅✅✅
stock✅❌✅
brand✅❌❌
license❌✅❌

✅ In SQL you'd need 3 separate tables or a massive table full of NULL values. In NoSQL — one collection handles them all cleanly!

🔍 Querying Mixed Schemas

JavaScript
// Works across ALL schemas
db.products.find({ price: { $lt: 100 } })

// Only matches docs WITH "type" field
db.products.find({ type: "digital" })

// Check if a field exists
db.products.find({ certifications: { $exists: true } })

7 · Time Complexity

Where n = number of documents  |  k = number of results returned

OperationNo IndexWith Index
InsertO(1)O(log n)
Find by _idO(1)O(1)
Find by fieldO(n)O(log n)
Find range queryO(n)O(log n + k)
Update by _idO(1)O(1)
Update by fieldO(n)O(log n)
Delete by _idO(1)O(1)
Delete by fieldO(n)O(log n)
Sort ($sort)O(n log n)O(n log n)
$lookup (join)O(n · m)O(n · log m)

📈 Scale Impact

DocumentsO(n) — No IndexO(log n) — Index
1,0001,000 ops~10 ops
100,000100,000 ops~17 ops
1,000,0001,000,000 ops~20 ops
100,000,000100,000,000 ops~27 ops
⚡ With 100 million documents, an index reduces operations from 100 million → just 27!

🧮 Aggregation Pipeline Stages

  • $match — O(n) without index, O(log n) with index
  • $group — O(n) — must process all matched documents
  • $sort — O(n log n) — always expensive
  • $limit — O(1) — just cuts the result
  • $lookup — O(n · m) — very expensive, use carefully!
⚠️ Always put $match first in aggregation pipelines to reduce documents processed by later stages.

8 · Indexing

An index is a separate data structure (B-Tree) that MongoDB maintains for fast lookups without scanning every document.

📚 Like the index at the back of a book — instead of reading every page, you jump directly to the right page.

🔍 Check Existing Indexes

JavaScript
db.products.getIndexes()
💡 MongoDB always creates an index on _id automatically — it can never be removed.

➕ Single Field Index

JavaScript
// Ascending
db.products.createIndex({ price: 1 })

// Descending
db.products.createIndex({ price: -1 })
💡 1 = Ascending  |  -1 = Descending

➕ Compound Index (Multiple Fields)

JavaScript
db.products.createIndex({ brand: 1, price: -1 })
💡 ESR Rule — order fields as: Equality first → Sort second → Range last

➕ Unique Index

JavaScript
db.products.createIndex(
  { name: 1 },
  { unique: true }
)
// Inserting a duplicate name will throw:
// E11000 duplicate key error ❌

➕ Text Index (Full-Text Search)

JavaScript
db.products.createIndex({ name: "text" })

// Now search by text
db.products.find({ $text: { $search: "organic tea" } })

➕ TTL Index (Auto-Delete)

JavaScript
// Auto-delete sessions after 1 hour
db.sessions.createIndex(
  { createdAt: 1 },
  { expireAfterSeconds: 3600 }
)
⏰ Perfect for: sessions, OTP codes, temporary carts — anything that should expire automatically!

➕ Partial Index

JavaScript
// Only index products actually in stock
db.products.createIndex(
  { price: 1 },
  { partialFilterExpression: { stock: { $gt: 0 } } }
)

🗑️ Drop an Index

JavaScript
db.products.dropIndex("price_1")   // by name
db.products.dropIndexes()          // drop ALL (except _id)

🔎 Explain — Verify Index Usage

JavaScript
db.products.find({ price: { $lt: 50 } }).explain("executionStats")
FieldGood ✅Bad ❌
winningPlan.stageIXSCAN (index scan)COLLSCAN (full scan)
totalDocsExaminedSmall numberEqual to total docs

📊 Index Types Summary

TypeSyntaxBest For

Compound{ f1: 1, f2: -1 }Multi-field queries

📁 Creating Collections

JavaScript
// Method 1: Implicit (auto-created on insert)
db.products.insertOne({ name: "Coffee Maker" })

// Method 2: Explicit
db.createCollection("customers")

// Method 3: With validation rules
db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["customerId", "totalAmount", "status"],
      properties: {
        status: {
          enum: ["pending", "shipped", "delivered", "cancelled"]
        }
      }
    }
  }
})

10 · When to Use / Avoid NoSQL

✅ Use NoSQL When…

  • Large volumes of data
  • Rapidly changing structure
  • High-speed read/writes
  • Distributed systems
  • Unstructured / semi-structured data
  • Horizontal scaling needed

❌ Avoid NoSQL When…

  • Complex table relationships
  • ACID transactions needed
  • Financial / banking data
  • Structured, predictable data
  • Complex joins & aggregations
